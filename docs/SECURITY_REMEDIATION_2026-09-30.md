# השלמת תיקוני האבטחה — Talk2Pay

תאריך: 30 בספטמבר 2026. התיקונים בוצעו בריפו בעקבות אישור המשתמש, לפי סדר השלבים שבדוח הסקירה. לא בוצעו פריסה, push, commit או שינויים במערכת הפעילה.

## התיקונים שבוצעו

| שלב | ממצאים | תוצאה |
| --- | --- | --- |
| 1 | SEC-01, SEC-02 | מיגרציה מפעילה RLS ושוללת הרשאות נתונים מ־PUBLIC/anon/authenticated בכל 27 טבלאות הסכמה. שירות השרת משתמש ב־service_role ובבדיקות ההרשאה הקיימות. פונקציות אימות מוגבלות לשרת, אימות Auth אינו מסתמך על דגל פרופיל, ואסימונים נצרכים באופן אטומי לפני אישור החשבון. |
| 2 | SEC-03 והזרקת שמות API keys | נתוני קבצי ייבוא, כותרות, אפשרויות מיפוי ושמות מפתחות מוצגים באמצעות DOM/textContent. תוכן HTML זדוני מוצג כטקסט. |
| 3 | SEC-04, SEC-05 | זכאות מנוי אחידה דורשת מסלול מוכר, מצב מנוי מותר ותוקף אמיתי. אין הענקת 30 יום בשל מידע חסר. הזמנה מסומנת כמשולמת רק אחרי payment_status=paid ואימות סכום, מטבע, עסק וסשן ספק במסד הנתונים. מעברים אטומיים מונעים נסיגה מתשלום מוצלח או החייאת הזמנה שבוטלה/הוחזרה. |
| 4 | SEC-06 | מתג 2FA הושבת, החיווי מציין שהאפשרות אינה זמינה, והדגלים הישנים מתאפסים במיגרציה. לא הוטמע MFA אמיתי; הוסרה ההבטחה המטעה בהתאם לחלופה שבדוח. |
| 5 | יתר הממצאים | איפוס סיסמה משתמש בלקוח Auth נפרד ובאסימון המשתמש שקיבל את קישור האיפוס. הדפדפן מסיר סודות מהכתובת ואינו משתמש בחשבון אחר ששמור בו. פעולות Auth מופרדות בין בקשות. תגובות פרופיל משתמשות ברשימת שדות מותרת. סודות WhatsApp מוצפנים בכתיבה וגם בהעברת ערכים ישנים. נוספו מגבלות קצב להתחברות ולפעולות Auth, ו־X-Forwarded-For מכובד רק דרך פרוקסי שהוגדר במפורש. תוקנה שגיאת SQL, נוספה פונקציית עדכון התשלום החסרה, ועליית השרת ממתינה לסיום המיגרציות. גרסאות Python שנבדקו קובעו באמצעות requirements.lock.txt. |

## אימות מקומי

- **22 בדיקות Python עברו**, כולל HTTP מול אפליקציית FastAPI המורכבת בפועל: הסתרת סודות, סגירת אימות מזויף, חד־פעמיות קוד, זכאות מנוי, תשלום מושהה, איפוס סיסמה מבודד, 2FA מושבת, הגבלת קצב, שרשרת פרוקסי והצפנת סודות.
- **בדיקות Chromium עברו** עם תאי ייבוא, כותרות ושמות מפתחות המכילים תג HTML עם event handler. התוכן נשאר טקסט ולא הורץ. נבדק גם שאיפוס סיסמה שולח את אסימון קישור השחזור לאחר אימותו, למרות חשבון אחר השמור בדפדפן.
- **PostgreSQL מקומי באמצעות PGlite** הריץ את bootstrap וכל שש המיגרציות ללא שינוי בקובצי SQL. נבדקו RLS והרשאות 27 טבלאות, חסימת anon/authenticated, אימות Auth, צריכת אסימון פעם אחת, דחיית אי־התאמה בסכום/מטבע/סשן ומניעת נסיגת מצב תשלום. תפקידי Supabase וסכמת auth הוגדרו בסביבה המבודדת לצורכי בדיקה.
- בדיקות תחביר Python, `pip check`, התקנת requirements במצב dry-run ו־`git diff --check` עברו.

בדיקות ספקי Auth/Stripe השתמשו במימושים מדומים; בדיקות מסד הנתונים והדפדפן היו מקומיות. לא נשלחו תשלומים, הודעות דוא״ל או בקשות לספקי הייצור. קיבוע גרסאות אינו תחליף לבדיקת CVE שוטפת, ולא נטען שבוצעה בדיקת CVE לכל התלויות.

## הרצת הבדיקות מחדש

```powershell
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
npm --prefix tests install
npm --prefix tests test
python -m compileall -q backend main.py
git diff --check
```

בדיקות הדפדפן משתמשות ב־Chrome מקומי כברירת מחדל. אפשר לשנות באמצעות PLAYWRIGHT_CHANNEL. משתני PLAYWRIGHT_MODULE ו־PGLITE_MODULE מאפשרים הפניה להתקנות קיימות. כלי הבדיקה ב־tests/package.json מקובעים לגרסאות שנבדקו.

## דרישות פריסה

1. להעלות את קוד השרת והדפדפן ואת שתי המיגרציות החדשות יחד. התיקונים בריפו אינם משנים לבדם את הרשאות מסד הנתונים הפעיל.
2. כאשר MIGRATIONS_AUTO_APPLY=true ו־DATABASE_URL מוגדר ללקוח בעל הרשאות מיגרציה, עליית השרת מפעילה מיגרציות בתוך טרנזקציה ונעילה, מצפינה את סודות WhatsApp הישנים וממתינה לסיום לפני קבלת בקשות. כאשר הפעלה אוטומטית כבויה או חסר DATABASE_URL, יש להפעיל את אותו תהליך מיגרציה בנפרד לפני חשיפת השרת. הרצת SQL בלבד אינה כוללת את העברת הסודות שבקוד Python.
3. המנגנון ממשיך לבדוק checksums של מיגרציות. תוקנה שגיאת פתיחת גוף הפונקציה בקובץ 20260920_payment_webhook_idempotency_functions.sql. אם במסד הקיים כבר רשומה גרסה אחרת של קובץ זה, יש להשוות ולהתאים את היסטוריית המיגרציות לגרסה שבוצעה בפועל; אין לעקוף את בדיקת ה־checksum או למחוק היסטוריה ללא בירור.
4. שלילת הרשאות טבלאות מתפקידי הדפדפן היא מכוונת. מסלולי הריפו פונים לנתונים דרך FastAPI. לקוח חיצוני שמסתמך על גישה ישירה לטבלאות יצטרך לעבור ל־API המאומת.
5. לשמור את SECRET_KEY/SECRET_KEY_CURRENT המשמש להצפנה באופן יציב ומוגן. להגדיר TRUSTED_PROXY_CIDRS רק לכתובות הפרוקסי האמינות בפועל, ולהתאים גם את הגדרות הפרוקסי של שרת ASGI. בפריסה מרובת עובדים יש להגדיר REDIS_URL כדי לשתף מגבלות קצב.
6. לאחר הפריסה לאמת הרשאות בפועל, זרימות הרשמה ואיפוס מול Supabase, allowlist של כתובת חזרת האיפוס ואירועי Stripe בסביבת בדיקות. חשיפה קודמת או ניצול קודם לא הוכחו בסקירה זו.
