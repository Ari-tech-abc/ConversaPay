# תיקוני מערכת המנויים — לפני חיבור ישראכרט

בוצעו תיקוני תשתית בקוד ובדיקות מקומיות. לא נשלחה פנייה לספק, לא נוצר חיוב אמיתי, לא הוחלה מיגרציה על מסד הנתונים החי ולא הוחלף ספק בפרודקשן.

## מה תוקן

| בעיה | ההתנהגות החדשה |
| --- | --- |
| לחיצה חוזרת יכולה לפתוח עוד תהליך רכישה | ניסיון רכישה נשמר במסד הנתונים. נעילת שורת המשתמש ואינדקס ייחודי מאפשרים ניסיון פתוח אחד למשתמש, גם בבקשות למסלולים שונים. |
| ניתוק אחרי פנייה לספק משאיר תוצאה לא ידועה | ניסיון חוזר משתמש באותו מזהה פעולה. לאחר חלון הבטיחות אין ניסיון חיוב חדש אוטומטי; הפעולה מסומנת לבדיקה. |
| חשבון שכבר מחויב יכול לרכוש מנוי נוסף | חוזה מנוי מקושר או תקופת שירות בתשלום חוסמים רכישה מקבילה. שינוי מסלול אינו מיושם באמצעות מנוי שני. |
| מחיר שמוגדר אצל הספק אינו תואם למחיר האתר | מחיר, מטבע ותקופת חיוב נבדקים מול קטלוג שרת מרכזי לפני יצירת מנוי. |
| חזרה לדף הצלחה אינה מוכיחה תשלום | נבדקים בעלות, סכום, מטבע, מצב תשלום והחשבונית העדכנית של המנוי. |
| תקופת ספק חדשה עלולה להיות תקופה שלא שולמה | גישה ניתנת רק עד לתקופת השירות שבשורת המנוי בחשבונית ששולמה. חשבונית קודמת אינה מממנת תקופה חדשה. |
| אישור חוזר מאפס את תאריך תחילת המנוי | נשמר תאריך התחלה קיים. עדכונים ישנים או של מנוי אחר אינם מחליפים מנוי פעיל. |
| פרופיל המשתמש והעסק מתעדכנים בנפרד | עדכון ההרשאות מתבצע בטרנזקציה אחת לשניהם. תקלה בעדכון העסק מבטלת גם את שינוי הפרופיל. |
| ביטול עלול להירשם בלי שנעצר החידוש אצל הספק | בקשת הביטול נרשמת תחילה. חידוש מסומן כמבוטל רק אחרי שהספק מאשר את מזהה המנוי והביטול. |
| תקופת גישה שפגה נראית כאילו אין יותר חיובים | סטטוס החידוש נשמר בנפרד מתוקף הגישה; ניתן לבטל חוזה מחייב גם אם הגישה כבר פגה. |
| החזר על עסקה עלול לבטל מנוי לפי לקוח משותף | אירוע החזר אינו מבטל מנוי שירות. בקשת החזר נשארת לבדיקה ואינה מוצגת כהחזר כספי שבוצע. |
| אישור שהגיע בזמן ניתוק עלול להישאר לא מסונכרן | כלי התאמה קורא מהספק מצב רכישה וביטול ומתקן רישומים. הוא אינו יוצר תשלום או מחייב כרטיס מחדש. |

## הפרדת הספקים

`SUBSCRIPTION_PROVIDER` שולט בגביית מנויי Talk2Pay בנפרד מ־`PAYMENT_PROVIDER` של הזמנות העסק. התמיכה הקיימת ב־Stripe נשמרה כספק מורשת מאחורי ממשק נפרד; לא נוצר חיבור Stripe חדש. בחירה ב־`isracard` ללא מימוש מאומת מחזירה הודעת חיבור חסר ואינה עוברת לספק אחר.

המחירים הקיימים נשמרו: Pro ב־200 ש״ח ו־Premium ב־350 ש״ח לחודש. לא נוספו מס, הנחה, תקופת ניסיון, עמלה, תקופת חסד או חיוב על שדרוג בלי הגדרת מדיניות מתאימה.

## בדיקות

- בדיקות HTTP ושירותים עם ספקים מדומים: ניתוק, ניסיון חוזר, סכום שגוי, חידוש שלא שולם, ביטול שלא אושר, אישור מאוחר והפרדת החזרים.
- בדיקות PostgreSQL באמצעות PGlite: המיגרציות עצמן, מניעת ניסיונות מקבילים, שיוך למשתמש, איסור קיצור תקופה מאירוע ישן, ביטול כפול, הגנות הרשאה וביטול טרנזקציה שלמה בעת תקלה.
- בדיקת מסך המנוי בעברית ובאנגלית, במחשב ובמובייל. כשאין חיבור זמין, הממשק אינו מציג אפשרות רכישה פעילה.

תוצאות בעותק נקי: 63 בדיקות Python עברו, בדיקות PostgreSQL לשני מסלולי הבדיקה עברו (12 קובצי SQL ו־36 טבלאות), ו־7 בדיקות שפה ותצוגה עברו במסך המנוי.

## הכנה להפעלה בהמשך

1. להחיל ולוודא את `database/migrations/20261116_subscription_operations.sql` לפני פריסת קוד המנויים החדש. היעדר פונקציות האחסון מונע יצירת checkout, במקום לפנות לספק ללא רישום בטוח.
2. כלי `scripts/reconcile_subscriptions.py` מציג סיכום ללא שינוי כברירת מחדל. `--apply` מאמת מול הספק ומעדכן אישורים; אינו יוצר חיוב. צריך להגדיר לו תזמון נפרד לאחר החיבור. הבדיקה מוגבלת ומסובבת פעולות שנבדקו כדי שלא להרעיב משתמשים אחרים.
3. רק לאחר השלמת עבודת המערכת, לאמת מול הספק את חשבון הבדיקות, ממשק ישראכרט בפועל והרשאת חיוב חוזר; לממש את המתאם ולבדוק אותו בסנדבוקס.
4. הפעלה חיה תכלול גם אימות המע״מ, מסמכים חשבונאיים ומדיניות ניסיונות גבייה. שינוי מסלול, עדכון כרטיס והחזר כספי אוטומטי דורשים מימוש ייעודי מול הספק ואינם מוצגים כאן כמושלמים.

מקורות טכניים למימוש המורשת: [בקשות חוזרות ללא כפילות](https://docs.stripe.com/api/idempotent_requests), [אירועי שרת](https://docs.stripe.com/webhooks), [תקופת שירות בשורת חשבונית](https://docs.stripe.com/api/invoice-line-item/object).
