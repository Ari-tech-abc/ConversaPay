# TALK2PAY — מסלול מכירה עם עובדות שמגיעות מהשרת

הצ׳אט באפליקציה מחובר כעת ל־Ollama ולמודל המאומן `talk2pay-sales-v1:latest` כברירת מחדל. חובר מודל v1 המיוצא שכבר מותקן במחשב; adapters של v2/v3 לא הוחלפו בו. זהו שינוי מקומי בקוד התזמור, ללא אימון חדש או פרסום לשרת.

## הפעלת החיבור המקומי

בפיתוח מקומי ברירת המחדל היא `AI_PROVIDER=ollama`, כתובת `OLLAMA_BASE_URL=http://127.0.0.1:11434`, מודל `OLLAMA_MODEL=talk2pay-sales-v1:latest` ומגבלת המתנה `OLLAMA_TIMEOUT_SECONDS=75`. ב־production ברירת המחדל נשארת Gemini; בחירת Ollama שם דורשת `AI_PROVIDER=ollama` ושירות Ollama זמין לשרת. Ollama צריך לפעול באותו מחשב שבו שרת האפליקציה פועל. כתובת localhost בשרת מרוחק אינה מתחברת למחשב האישי. אין מעבר אוטומטי לשירות ענן בכשל. אפשר לבחור Gemini במפורש באמצעות `AI_PROVIDER=gemini` ומפתח תקין. חילוץ הפעולה פועל עם `think=false` כדי שמגבלת הטוקנים תשמש לפלט JSON ולא לטקסט חשיבה פנימי.

בדיקת המודל דרך מסלול הצ׳אט, עם מסד וספק תשלום מדומים:

```powershell
.venv\Scripts\python.exe scripts/test_local_sales_integration.py
```

הדוח נכתב ב־`artifacts/verified-sales/local-model-integration.json`. הבדיקה מפעילה inference אמיתי ואישור הצעה דרך `/api/v1/chat`; אין בה תשלום אמיתי. היא אינה מבחן חנות מלאה: הקטלוג קטן והשיחות הן מקרי פיתוח, ללא עומס משתמשים מקביל.

להרצת האפליקציה מול עסק אמיתי נדרשות גם הגדרות Supabase, SECRET_KEY ושאר הגדרות האפליקציה הקיימות. כרגע אין בקובצי הפרויקט המקומיים סביבה מלאה שמאפשרת להפעיל את השרת מול חנות אמיתית; הבדיקות משתמשות בערכי בדיקה מבודדים. לאחר הגדרת הסביבה מריצים `.venv\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000`. אין לחשוף את שירות Ollama לאינטרנט.

## מה הוטמע

### חיבור Oracle דרך Cloudflare Access

השרת ב־Oracle מריץ Ollama על `127.0.0.1:11434`. Cloudflare Tunnel מקשר אליו את `https://model.conversapay.org`; אפליקציית Access על כל הכתובת משתמשת במדיניות `Service Auth` שמאפשרת רק את הטוקן `talk2pay-render`.

הקוד תומך בשני משתני סביבה סודיים ב־Render: `OLLAMA_CF_ACCESS_CLIENT_ID` ו־`OLLAMA_CF_ACCESS_CLIENT_SECRET`. יש להזין את הערכים ישירות ב־Environment של השרת; אין להוסיף אותם ל־Git או לקוד הדפדפן. שני הערכים נדרשים יחד ומועברים בכותרות Cloudflare בשיחות ובסיכומים. כאשר מוגדרים סודות נדרש endpoint של HTTPS; הלקוח אינו עוקב אחר הפניות HTTP.

לאחר פרסום הקוד המעודכן ובדיקה עם הטוקן, הגדרות ההפעלה הן `AI_PROVIDER=ollama`, `OLLAMA_BASE_URL=https://model.conversapay.org`, `OLLAMA_MODEL=talk2pay-sales-v1:latest`. אין להפעיל את הספק המרוחק לפני פרסום התמיכה בכותרות האימות. יש למדוד את זמני המודל על Oracle ולבדוק שיחה מלאה לאחר המעבר; בדיקת 403 ללא הרשאה מוכיחה חסימת Access, אך אינה מוכיחה חיבור מוצלח ל־Ollama.

המודל מחזיר SalesPlan מוגדר: סוג בקשה, קוד מוצר, כמות, תקציב ואיסוף/משלוח. שדות של מחיר, קישור, אישור תשלום או טקסט חופשי אינם מותרים בפלט המודל. Ollama מקבל JSON schema עם קודי מוצרים מותרִים בלבד, תקציב מספרי והוראות בעברית ובאנגלית. המודל אינו מקבל מחירי קטלוג. הפלט נבדק שוב עם Pydantic; פלט לא תקין, קטוע, כשל או timeout מחזירים בקשת הבהרה קבועה. שירות Gemini נשאר כאפשרות מפורשת עם SDK אסינכרוני ומגבלת המתנה של 22 שניות. שם הקובץ gemini_service נשמר לתאימות; השירות בו תומך בשני הספקים.

מחירים מחושבים ב־Decimal מתוך מוצרים פעילים של העסק הנוכחי, עם מלאי מספיק. חיפוש המוצרים מוגבל לקטלוג שהוחזר; אין הבטחה שזו כל רשימת המוצרים. התשובה מציינת זאת כאשר לא נמצאה התאמה. המימוש הראשוני תומך ב־ILS, מוצר אחד להצעת checkout וכמות 1–100.

בקשת רכישה מחזירה קודם הצעת מחיר חתומה ותקפה ל־10 דקות. הלקוח מאשר בכפתור ב־widget. השרת בודק חתימה, עסק, שיחה, תוקף ומחיר/מלאי/תנאים עדכניים, ורק אז יוצר הזמנה וקישור אצל ספק התשלום. order_number נגזר ממזהה ההצעה וייחודי במסד הקיים, כך ששליחה חוזרת של אותו אישור אינה יוצרת הזמנה נוספת. במקרה checkout שתקוע/נכשל אין ניסיון אוטומטי נוסף ואין הודעת הצלחה שהומצאה.

קישור צריך להיות HTTPS ללא פרטי גישה ב־URL. סכום וסטטוס pending נכתבים בקוד מתוך ההזמנה. אין המצאת מועד תפוגה. שאלת מצב תשלום נענית מתוך הזמנה אחת השייכת לעסק ולשיחה; אישור דורש גם רשומת payment במצב succeeded עם סכום ומטבע תואמים ומזהה סשן ספק. סימון ההזמנה בלבד אינו מספיק. טענת לקוח ששילם אינה מעדכנת דבר. כמה הזמנות בשיחה דורשות בירור. בקשת תוקף קישור נפרדת מועברת לבירור: במימוש הנוכחי אין כלי שמחזיר מועד תפוגה מאומת.

היסטוריית השיחה נשמרת אחרי הרכבת התשובה הסופית, ונקראות ההודעות האחרונות לפי סדר כרונולוגי. ה־widget מציג מחיר וכמות, מאפשר אישור מקלדת, מונע לחיצה כפולה ויש לו timeout של 110 שניות לבקשת HTTP כדי להכיל את מגבלת המודל המקומי ואת יצירת הקישור.

## הגדרות שנדרשות לבדיקה עם עסק אמיתי

עלות משלוח/איסוף חייבת להיות מפורשת ב־business.settings, לדוגמה:

```json
{"shipping_ils":"17.00","pickup_ils":"0.00","shipping_business_days":[2,5]}
```

זהו פורמט הגדרות חדש למסלול הזה; הוא לא נשמר אוטומטית בעסק קיים ולא הוספו עדיין שדות עריכה במסך ההגדרות. ללא עלות מאומתת המסלול יבקש בירור וימנע checkout. חשבון PRO/PREMIUM וספק checkout מוגדר נדרשים ליצירת קישור. לינק מוצר קבוע אינו מוכיח סכום או סטטוס ולכן אינו משמש לעקיפת התהליך.

## בדיקה והגבלות

בדיקות יחידה ו־HTTP משתמשות בנתוני מסד וספקים מדומים בלבד, בלי קריאה למודל חי ובלי יצירת תשלום אמיתי. הן מכסות גבול תקציב, דיוק כספי, מלאי, בידוד עסק, מידע חסר, שדות מומצאים, אישור חתום, שינוי מחיר/מלאי אחרי הצעה, מניעת replay וכשל provider. בדיקת Chromium בודקת את כפתור האישור ואת הקישור בתצוגת mobile.

אין כאן הוכחה שהמודל מבין כל בקשה או מנהל שיחה טבעית מלאה. בחירת כוונה/כמות/אופן קבלה עדיין יכולה להיות שגויה; הצעת האישור הגלויה נועדה לאפשר ללקוח לבדוק זאת. שיחות כלליות, הנחות, כמה מוצרים, מטבעות נוספים ופעולות refund דורשות הרחבה מבוקרת.

בדיקת מלאי אינה reservation אטומי ואינה מונעת overselling מול הזמנות מקבילות אחרות. נדרש מסלול שמירת מלאי בעסקאות מסד לפני שימוש אמיתי רחב. timeout לא מוכיח שהספק לא יצר checkout; לכן ההזמנה נשארת וצריך reconciliation/בדיקת נציג במקרה לא ודאי.

המודל המאומן חובר ונבדק מקומית. יש להמשיך לבדיקת שיחות עצמאית עם קטלוג גדול ומצבים עמומים, בדיקת בסיס להשוואה, עומס, שמירת מלאי ואינטגרציה עם sandbox של ספק התשלום לפני שימוש בלקוחות אמיתיים. אין אישור production במסגרת השינוי הזה.
