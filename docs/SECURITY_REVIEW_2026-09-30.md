# סקירת אבטחה — Talk2Pay

תאריך: 30 בספטמבר 2026. בסיס הסקירה: commit `e20555b`, עץ עבודה נקי בתחילת הבדיקה.

הסקירה כללה את מבנה הריפו, מסלולי השרת הרשומים ב־main.py, אימות והרשאות, גישה לנתוני עסקים, סכמת SQL ומיגרציות, תשלומים, ווידגט, קוד הדפדפן, פלאגין WordPress, סקריפטים והגדרות פריסה. בוצעו חיפושים רוחביים וקריאה ממוקדת של זרימות האבטחה. זו סקירת קוד ולא בדיקת חדירה או הבטחה שכל פרצה אותרה.

לא שונו קובצי יישום, לא הורצו מיגרציות, לא נקראו ערכי סודות ולא בוצעו בקשות למערכת הפעילה. הדוח הוא הקובץ היחיד שנוסף. גרסאות התלויות המותקנות וההרשאות בפועל ב־Supabase לא נבדקו; requirements.txt ברובו אינו מקבע גרסאות.

## ממצאים בעדיפות גבוהה

### SEC-01 — טבלאות רגישות ללא הגנות RLS בסכמת הריפו

**חומרה: קריטית אם קיימות הרשאות Data API לטבלאות. מצב: פער מוכח בסכמה; החשיפה בפרודקשן טרם אומתה.**

מיקום: `database/full_schema_bootstrap.sql:9`, `:167`, `:285`, בלוק ההגנות `:416` ואילך.

הסכמה יוצרת שמונה טבלאות שאינן נכללות בהפעלת RLS או בשלילת הרשאות מהתפקידים הציבוריים: `profiles`, `messages`, `usage_logs`, `admin_users`, `admin_audit_logs`, `domain_restrictions`, `abuse_reports`, `refund_requests`.

הסיכון המרכזי הוא `profiles`: היא מכילה תפקיד, מסלול מנוי, אסימון אימות דוא״ל ופרטי WhatsApp. אם קיימות הרשאות SELECT/UPDATE לתפקידי anon/authenticated, אפשר להגיע ישירות דרך Supabase ולעקוף את בדיקות FastAPI, לקרוא מידע של משתמשים אחרים או לשנות מצב מנוי ותפקיד. חשיפת `messages` מאפשרת קריאת שיחות בין עסקים; `admin_users` מכילה גם גיבובי סיסמאות.

הגנות על טבלאות קשורות אינן מגינות אוטומטית על טבלאות אלה. מפתח anon ציבורי הוא תקין כשלעצמו; הבעיה היא הרשאות הטבלאות ללא בידוד מתאים.

**תנאי חשוב:** פרויקטי Supabase ותיקים עשויים להחזיק grants אוטומטיים, בעוד שברירות המחדל בפרויקטים חדשים השתנו. גם RLS שהוגדר ידנית מחוץ לריפו עשוי למנוע ניצול. אי אפשר לקבוע מהקוד בלבד שהמידע חשוף כעת.

**אימות שבוצע:** מיפוי שמות הטבלאות מול הפעלות RLS הישירות והלולאה הדינמית בסכמה. שמונה הטבלאות לעיל חסרות. לא נמצאה במיגרציות בריפו השלמה של ההגנות שלהן.

**תיקון מוצע לאחר אישור:** מיגרציה חדשה שמגדירה RLS והרשאות מינימליות לכל הטבלאות; הגבלת שדות רגישים בפרופיל לשרת; בדיקות בידוד בין שני משתמשים. לפני פריסה, לבדוק בפועל `pg_class`, `pg_policies` ו־grants תחת anon/authenticated.

מקור: [Supabase — Securing your API](https://supabase.com/docs/guides/api/securing-your-api), [שינוי ברירות המחדל להרשאות](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

### SEC-02 — עקיפת אימות דוא״ל דרך RPC ציבורי ומסלול תיקון Auth

**חומרה: גבוהה. מצב: שרשרת הרשאות פגומה מוכחת בקוד; לא נוסתה מול בסיס הנתונים הפעיל.**

מיקום: `database/full_schema_bootstrap.sql:372`–`:379`, `backend/routers/onboarding.py:137`–`:149`.

`mark_email_verified(p_user_id)` היא פונקציית SECURITY DEFINER שמקבלת מזהה משתמש, מסמנת את הפרופיל כמאומת ומוחקת את אסימון האימות. היא ניתנת במפורש להרצה על ידי anon ו־authenticated, ללא בדיקת זהות, קוד או בעלות.

`POST /api/v1/auth/verify-code` מחמיר את הפער: אם שדה הפרופיל כבר מסומן כמאומת, הוא מאשר גם את הדוא״ל ב־Supabase Auth באמצעות הרשאת admin ומחזיר הצלחה לפני בדיקת הקוד.

לכן מי שיודע את מזהה המשתמש יכול לסמן פרופיל כמאומת דרך RPC ואז להגיש בקשת verify-code עם קוד שרירותי בן שש ספרות. התוצאה היא אישור חשבון בלי הוכחת גישה לתיבת הדוא״ל. השגת המזהה תלויה בזרימת ההרשמה/הרשאות DB; SEC-01 עלולה לחשוף אותו ישירות.

זה אינו מוכיח השתלטות על חשבון קיים שסיסמתו אינה ידועה. הוא מאפשר לעקוף את מנגנון הוכחת הבעלות על דוא״ל בחשבונות שהמתקיף יצר או יודע את סיסמתם.

**תיקון מוצע לאחר אישור:** לשלול EXECUTE מתפקידים ציבוריים ולהשאיר service_role בלבד; להסיר אישור Auth שנובע רק מדגל בפרופיל; לאשר Auth לאחר בדיקת הוכחה תקפה ולצרוך את ההוכחה באופן אטומי.

### SEC-03 — הזרקת JavaScript בתצוגת קובצי ייבוא

**חומרה: גבוהה. מצב: זרימת נתונים לא מסוננת מוכחת בקוד; ביצוע בדפדפן לא נוסה.**

מיקום: `frontend/html/product-import.html:19`–`:22`, `main.py:35` (CSP).

כותרות ושדות מתוך Excel/CSV/TSV מוזרקים ל־innerHTML בתצוגה המקדימה ובאפשרויות מיפוי העמודות. `normalize()` רק מסיר רווחים ואינו מבצע escaping. מסמך שמכיל תג HTML עם event handler יכול להריץ JavaScript כשהמשתמש טוען אותו, עוד לפני לחיצה על כפתור הייבוא.

העמוד מחזיק JWT של המשתמש מתוך localStorage/sessionStorage. קוד זדוני באותו origin יכול לקרוא את הטוקן או לבצע פעולות API בהרשאות בעל העסק. התרחיש דורש שהקורבן יפתח קובץ בשליטת המתקיף, למשל קטלוג שנשלח מספק. מדיניות CSP כוללת unsafe-inline ואינה חוסמת event handlers אלה.

**תיקון מוצע לאחר אישור:** לבנות את התצוגה עם createElement/textContent ולהגדיר ערכי option דרך DOM properties; לא לשלב מידע מהקובץ בתוך HTML. להוסיף בדיקת דפדפן מקומית עם מטען שמסמן דגל בלבד, ללא גניבת נתונים.

### SEC-04 — מנוי שטרם שולם מאפשר Checkout בתוכנית בתשלום

**חומרה: גבוהה. מצב: שוחזר מקומית בפונקציות המקור עם בסיס נתונים מדומה.**

מיקום: `backend/routers/stripe_webhook.py:123`, `backend/services/subscription_service.py:106`–`:129`, `backend/middleware/auth.py:90`, `backend/routers/chat.py:164` ואילך.

אירועי `customer.subscription.*` מוחלים גם כשהמנוי במצב incomplete. `apply_subscription_state()` שומר את מסלול PRO/PREMIUM במצבים אלה, ואם חסר תאריך סיום הוא יוצר תוקף של 30 יום. `active_plan()` מתחשב במסלול ובתאריך בלבד, ללא subscription_status. הצ׳אט משתמש בו כדי לאפשר Checkout.

בדיקה מבודדת של פונקציות המקור עם `subscription_status='incomplete'` ו־`plan_type='premium'` החזירה:

```json
{"isolated_subscription_status":"incomplete","stored_plan":"premium","effective_chat_plan":"premium","fallback_expiry_created":true}
```

המשמעות היא שלפחות במסלול הצ׳אט, בעל עסק יכול לקבל יכולת Checkout של תוכנית בתשלום בזמן שהמנוי טרם אושר לתשלום. דשבורד ומפתחות API כן שוללים incomplete, ולכן אין להסיק שכל התכונות נפתחות. משך הניצול בפועל תלוי בתאריכי Stripe ובאירועים הבאים.

**תיקון מוצע לאחר אישור:** החלטת זכאות אחת לכל הראוטרים, שמאשרת רק מצבי מנוי המותרים לפי המדיניות; לא להעניק 30 יום בשל מידע חסר; לא לפתוח Checkout למנוי incomplete/paused/לא ידוע.

מקור: [Stripe — Subscription statuses](https://docs.stripe.com/billing/subscriptions/overview#subscription-statuses).

### SEC-05 — הזמנה מסומנת כמשולמת לפני אישור התשלום

**חומרה: גבוהה כשאמצעי תשלום מושהים זמינים. מצב: שוחזר בענף ה־webhook עם אירוע מדומה.**

מיקום: `backend/routers/stripe_webhook.py:107`–`:111`, `backend/services/stripe_service.py:120` ואילך.

`checkout.session.completed` מסמן הזמנה כ־paid ותשלום כ־succeeded ללא בדיקת payment_status. Stripe יכולה לשלוח אירוע סיום Checkout כשהתשלום עדיין unpaid עבור אמצעי תשלום מושהים. לאחר מכן הוא עשוי להיכשל.

בדיקה מבודדת הפעילה את פונקציית המקור עם completed/payment_status=unpaid. אימות החתימה, ה־DB ושאר השירותים הוחלפו במימושים מדומים. הקוד ביקש לכתוב:

```json
{"order_status":"paid","payment_status":"succeeded","paid":true}
```

לא נבדק אילו אמצעי תשלום זמינים בחשבון Stripe הפעיל. הקוד אינו מגביל אותם במפורש לכרטיסים. אין כאן עקיפת חתימת webhook: הפער הוא בפרשנות אירוע חתום ואמיתי. אספקת סחורה על סמך paid עלולה להתרחש לפני קבלת הכסף.

**תיקון מוצע לאחר אישור:** להשאיר הזמנה pending/processing כשהתשלום unpaid; לסמן paid רק אחרי אישור תשלום מתאים; לאמת קישור להזמנה, סכום ומטבע, ולשמור על מעברים תקינים גם באירועים כפולים או מחוץ לסדר.

מקור: [Stripe — הנחיות Checkout ו־fulfillment](https://github.com/stripe/ai/blob/main/skills/stripe-best-practices/references/payments.md).

### SEC-06 — מתג 2FA מציג הגנה שאינה ממומשת

**חומרה: גבוהה ביחס להגנת החשבון המובטחת. מצב: מוכח בקוד היישום; הגדרות MFA חיצוניות לא נבדקו.**

מיקום: `backend/routers/profile.py:102`–`:105`, `backend/routers/auth.py:337`, `backend/middleware/auth.py:37`, `frontend/html/settings.html`.

הפעולה `/profile/2fa/toggle` משנה רק את `profiles.two_factor_enabled`. לא קיימים במסלול זה רישום גורם שני, challenge, אימות קוד או בדיקת assurance level באימות JWT. גם ההתחברות אינה משתמשת בשדה כדי לדרוש גורם שני.

משתמש שמפעיל את המתג מקבל חיווי שאימות דו־שלבי פעיל, אך סיסמה או טוקן תקפים ממשיכים להספיק לפי הקוד. זה אינו מאפשר כניסה ללא סיסמה; הוא מבטל את ההגנה הנוספת שהמשתמש סבור שקיבל.

**תיקון מוצע לאחר אישור:** לממש MFA אמיתי עם enrollment/challenge/verify ואכיפת AAL מתאימה; לחלופין להסיר את ההפעלה והחיווי עד שקיימת הגנה אמיתית.

## ממצאים נוספים שדורשים טיפול

- `backend/routers/auth.py:702`: אסימון האיפוס נשלח כפרמטר השני של `supabase.auth.update_user`. ב־SDK הנוכחי פרמטר זה הוא options, ולא JWT; העדכון משתמש ב־session של הלקוח. מחרוזת תגרום לשגיאה במקום להוכיח זהות. אין בסיס לטענה שזה מאפשר השתלטות כרגע. יש לתקן גם שימוש בלקוח Auth גלובלי משותף ולהפריד לקוחות לפי בקשה. מקור: [קוד SDK הרשמי](https://github.com/supabase/auth-py/blob/main/supabase_auth/_sync/gotrue_client.py).
- `database/migrations/20260920_payment_webhook_idempotency_functions.sql:15`: פתיחת גוף הפונקציה היא `as $` וסגירתו `$$;`. זו שגיאת SQL שצפויה להפיל את טרנזקציית המיגרציות. לא הורצה מול PostgreSQL. בנוסף, הקריאה ל־`update_order_payment_atomic` אינה מגובה בהגדרת פונקציה בריפו, ולכן תפקוד מסלולי התשלום תלוי בפונקציה חיצונית קיימת.
- `main.py`: סדר רישום הראוטרים מאפשר ל־onboarding `/auth/me` להקדים את SafeMeResponse ולהחזיר את הפרופיל המלא, כולל שדות סודיים, לבעל החשבון. מנגנוני הצפנת WhatsApp קיימים בקובץ שירות אך אינם מחוברים למסלול העדכון. זה מגדיל את הנזק של SEC-01/SEC-03.
- `frontend/html/settings.html:13`: שמות API keys מוזרקים ל־innerHTML ללא escaping. זהו sink נוסף של XSS; במסלול הרגיל יצירת השם דורשת הרשאת אותו בעל עסק, ולכן לא דורג כאן כפרצה עצמאית בין משתמשים.
- `backend/middleware/rate_limiter.py:46`: הסתמכות על כתובת ראשונה ב־X-Forwarded-For דורשת שהפרוקסי יסיר קלט בלתי מהימן. אין קונפיגורציית פרוקסי מספקת בריפו לקבוע אם ניתן לעקוף את מגבלות הקצב בפריסה. `/auth/login` אינו מכוסה במגבלת הקצב המקומית; יש לבדוק גם את מגבלות Supabase.

## סדר תיקון מוצע

1. SEC-01 ו־SEC-02: הרשאות DB, הגנה על פרופילים/שיחות וסגירת שרשרת אימות הדוא״ל.
2. SEC-03: הסרת הזרקת HTML מנתוני ייבוא ומ־API keys.
3. SEC-04 ו־SEC-05: איחוד זכאות מנוי ומעברי מצב התשלום.
4. SEC-06: החלפת מתג 2FA בהגנה אמיתית או הסרת החיווי המטעה.
5. לתקן חסימות מיגרציה ואיפוס סיסמה, ולבדוק שגרסאות התלויות וההרשאות בפריסה תואמות לקוד.

עדכון: המשתמש אישר תיקון בשלבים. התיקונים והאימות המקומי מתועדים ב־[דוח השלמת התיקונים](SECURITY_REMEDIATION_2026-09-30.md). התיאור לעיל משקף את מצב הריפו לפני התיקון. אין בדוח הוכחה שהמערכת כבר נוצלה.
