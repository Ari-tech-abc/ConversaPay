# חיבור WhatsApp לבדיקות

החיבור הנוכחי מיועד למספר הבדיקה של Meta. הוא מקבל הודעות טקסט, מחפש מוצרים אמיתיים בקטלוג העסק ושולח תשובה. הוא אינו מפעיל Gemini, יוצר הזמנות, שולח קישורי סליקה או שולח קמפיינים. כך בדיקת החיבור אינה צורכת קריאות AI בתשלום. במספר הבדיקה יש להשתמש רק בנמענים שאומתו ב־Meta.

Meta מציעה גישה חינמית למספרי בדיקה ב־[Developer Hub](https://whatsappbusiness.com/developers/developer-hub/). ההגבלה ל־5 נמענים כאן היא גם הגנה מקומית. אין להסיק ממסלול הבדיקה שמספר עסקי רגיל או אירוח השרת יהיו תמיד ללא עלות.

## פתיחת אפליקציה והודעה ראשונה

1. היכנסו ל־[Meta for Developers](https://developers.facebook.com/apps/) עם חשבון Facebook. אם Meta מבקשת, השלימו רישום כמפתח ואימות חשבון.
2. צרו אפליקציה והוסיפו את האפשרות **Connect with customers through WhatsApp**. אם Meta מבקשת לבחור או ליצור Business Portfolio, השלימו את ההנחיות. אין להוסיף אמצעי תשלום או מספר עסקי רגיל עבור הבדיקה הזאת.
3. באזור WhatsApp חפשו **API Setup**, **API Testing** או **Getting Started**. ממשק Meta עשוי להשתנות. בחרו את **מספר הבדיקה שסיפקה Meta**.
4. הוסיפו את הטלפון שלכם לרשימת נמעני הבדיקה ב־Meta ואמתו אותו לפי ההוראות. שלחו את הודעת הבדיקה מתוך Meta ובדקו שהיא הגיעה ל־WhatsApp בטלפון שלכם.
5. העתיקו **Phone Number ID** ואת **Access Token** הזמני. המזהה אינו מספר הטלפון. אין להדביק אסימונים בשיחה, בגיטהאב או בצילום מסך.
6. אחרי שהשרת הוכן לפי הסעיף הבא, פתחו באתר **הגדרות → WhatsApp**. הזינו את המזהה, האסימון ואת טלפון הנמען עם קידומת מדינה, למשל `972501234567`. שמרו.
7. העתיקו את **Callback URL** ואת **Verify Token** שהופיעו אחרי השמירה להגדרות Webhooks של אפליקציית Meta. לחצו **Verify and save**, והירשמו לשדה **messages** של `whatsapp_business_account`.
8. מהטלפון המאומת שלחו הודעת טקסט למספר הבדיקה, למשל שם מוצר שקיים בקטלוג. בהגדרות לחצו **רענון מצב**. מצב `accepted` אומר ש־Meta קיבלה את הבקשה; `delivered` אומר שהמענה נמסר, ו־`read` שהוא נקרא.

אם Meta אינה מספקת מספר בדיקה או דורשת אמצעי תשלום בשלב מסוים, עצרו ובדקו שאתם בתהליך הבדיקה. אין לעבור למספר רגיל כדי לעקוף את המגבלה. אין צורך בספק צד שלישי בתשלום בחיבור הזה.

## הכנת השרת — פעם אחת

האפליקציה משתמשת ב־Meta App אחד של מפעיל המערכת. **App Secret** של אותו App נדרש רק בשרת. התצורה אינה תומכת כרגע בחיבור Apps שונים של לקוחות; זה ידרוש אימות חתימות לכל App ותהליך onboarding נפרד.

1. הפעילו את המיגרציה החדשה `database/migrations/20261004_whatsapp_test_integration.sql` אחרי מיגרציות הפרויקט הקיימות. אם `MIGRATIONS_AUTO_APPLY=true` ו־`DATABASE_URL` מוגדר, המפעיל הקיים יפעיל אותה בעליית השרת. אם המיגרציות מופעלות ידנית, הפעילו את הקובץ דרך SQL Editor והמתינו לרענון PostgREST. שינוי זה אינו משנה קבצי מיגרציה שכבר הופעלו.
2. במנהל הסודות של סביבת הבדיקה הגדירו:

   ```dotenv
   WHATSAPP_ENABLED=true
   WHATSAPP_APP_SECRET=<App Secret של אותה אפליקציית Meta>
   WHATSAPP_TEST_PHONE_NUMBER_IDS=<Phone Number ID של מספר הבדיקה בלבד>
   WHATSAPP_GRAPH_VERSION=v23.0
   BACKEND_URL=https://<public-test-host>
   ```

   ניתן להשתמש ב־`META_APP_SECRET` כחלופה ל־`WHATSAPP_APP_SECRET`. גרסת Graph API ניתנת לשינוי לגרסה נתמכת של האפליקציה; אין להסיק שברירת המחדל היא הגרסה החדשה ביותר. ה־Access Token נשמר מתוך טופס ההגדרות, מוצפן, ולא במשתנה ציבורי.
3. ודאו שמזהה המספר ברשימת ההיתר הוא **נכס בדיקה של Meta**. אין להוסיף מזהה של מספר רגיל לרשימה. הקוד מגביל את הרשימה אבל אינו יכול להסיק מחיר או סוג נכס ממספר מזהה שרירותי.
4. הפעילו מחדש את השרת. ה־Worker משתמש באותה Supabase ובטבלאות החדשות; לא נדרש שירות תורים בתשלום. קבלת callbacks דורשת כתובת HTTPS ציבורית. שרת localhost בלבד אינו נגיש ל־Meta; אפשר להשתמש בסביבת הבדיקה הקיימת או במנהרה מתאימה ולבדוק את תנאיה בנפרד.

השרת כבוי כברירת מחדל. עד להכנתו האתר מציג שהחיבור טרם הופעל, עם מדריך זמין וטופס שמירה מושבת.

## מה נבדק ומה נשמר

- רק בעל העסק עם אימייל מאומת רשאי לשמור, לקרוא מצב או לנתק את החיבור. אין צורך בשדרוג מסלול עבור בדיקת המספר.
- ה־Access Token וה־Verify Token מוצפנים. GET אינו מחזיר אף אחד מהם. אסימון האימות מוצג פעם אחת אחרי שמירה; שמירה נוספת מחליפה את פרטי החיבור, מבטלת טיפול באירועים ישנים ודורשת אימות Webhook מחדש.
- GET verification מחזיר את `hub.challenge` רק כאשר האסימון מתאים. POST מאומת מול `X-Hub-Signature-256` על גוף הבקשה המקורי, לפני טיפול בהודעות.
- הודעות מנותבות גם לפי חיבור וגם לפי `metadata.phone_number_id`; נמענים מחוץ לרשימה אינם מקבלים תשובה. אין API לשליחת הודעות יזומות.
- הודעות נשמרות בתור לפני החזרת 200. מזהה Meta ייחודי מונע טיפול כפול ב־callbacks חוזרים. טיפול בתור שומר סדר לכל נמען.
- השרת מסרב להשיב אחרי 23 שעות מההודעה, כדי להשאיר מרווח לחלון השירות. הוא אינו מנסה לשלוח תבנית בתשלום כחלופה.
- תשובה שמצב שליחתה אינו ודאי אינה נשלחת שוב אוטומטית. `unknown` מצריך בדיקה ב־Meta. הודעות מוקלטות בשיחת העסק בערוץ `whatsapp`; רישום תשובת העוזר אינו אישור מסירה.
- טבלאות החיבור והתור חסומות ל־anon ול־authenticated ונגישות רק לשרת. התור מנוקה לאחר 30 יום; היסטוריית השיחות נשארת לפי מדיניות השיחות הקיימת. ניתוק מוחק את הסודות ואת התור, אך אינו מוחק שיחות שנרשמו.

## פתרון תקלות

- **השרת טרם הופעל:** לבדוק את משתני הסביבה, המיגרציה ומספר הבדיקה המורשה.
- **אסימון לא תקף / meta_190:** ליצור Access Token חדש מאותו App, לשמור שוב ולבצע Verify מחדש.
- **Webhook ממתין לאימות:** לבדוק HTTPS ציבורי, Callback URL, אסימון האימות ו־App Secret בשרת. אסימון שנוצר בשמירה קודמת כבר אינו תקף.
- **Meta שולחת אירוע בדיקה אבל אין הודעות מהטלפון:** לוודא הרשמה ל־`messages`, בחירת נכס הבדיקה הנכון ואימות הנמען ב־Meta. אירוע בדיקה עם Phone Number ID לדוגמה אינו שיחה אמיתית ואינו גורם לתשובה.
- **accepted בלי delivered:** לא לטעון שההודעה נמסרה. לבדוק את סטטוס המסירה ב־Meta ואת callbacks של statuses.

## אימות מקומי ללא ספקים

הריצו את בדיקות ה־API/Worker, את בדיקות SQL ואת בדיקות הדפדפן המצורפות. הן מדמות את Meta ואינן שולחות הודעות, מפעילות AI או נוגעות במסד production. בדיקה אמיתית מול Meta עדיין דורשת חשבון, מספר בדיקה, תצורת שרת ו־Webhook ציבורי.
